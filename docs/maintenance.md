# 项目维护与上游跟随策略

本文集中定义维护与验收规则，贡献步骤见[贡献指南](../CONTRIBUTING.md)。策略的采纳不代表相关实现、CI 或验收已经完成。提案、决议与阶段计划通过社区 issue 跟踪。

## 1. 项目边界

项目跟随上游 TorchTitan `main`，复用模型、配置、训练入口和资源下载工具，维护必要的 Ascend 适配与优化。实现遵循 [AGENTS.md](../AGENTS.md)：通用修复优先提交所属上游；硬件实现通过所选版本的 override 机制接入，补丁按第 4 节管理。本仓不复制独立的 Trainer、Engine 或配置解析器；允许通过合适的扩展接口或小范围继承实现必要差异并保留上游生命周期，外部并行库不得接管训练流程。技术职责与扩展约束见 [ARCHITECTURE](../ARCHITECTURE.md)。通用底层 kernel 优先贡献给对应算子库，本仓主要维护组件与适配。

上游尚未支持的模型遵循所选 TorchTitan 版本的模型适配规范，暂时托管于 `torchtitan_ascend/models/`，向 TorchTitan 提交 PR；上游合入并进入所用基线后复用上游实现，保留必要的 Ascend 适配。

核心能力优先复用 TorchTitan 已有实现，候选范围参考 [TorchTitan Features](https://github.com/pytorch/torchtitan#features)；新增能力说明实现归属和采用理由。Ascend 后端优化通过 override 或正式扩展接口接入，关联其服务的核心能力或模型组件及参考路径。保留上游特定硬件和实验实现的适用条件，不推导其在 Ascend 可用。

跟踪上游包括识别、评估和记录变化，不承诺支持全部上游能力。候选、优先级和采纳讨论在社区 issue 中维护；经评审的支持组合与证据入口记录在相关模型文档或公开评审记录中。模型另附上游来源。

## 2. 基线与支持状态

**候选基线**是待评估的代码、依赖和补丁组合；**已验证基线**是该组合在明确场景下通过验收并完成评审后的记录。上游 main 指 `pytorch/torchtitan` 的 `main`，不能以浮动分支或包版本号替代受测提交。

主线只维护一个当前已验收的 TorchTitan 基线，历史组合保留用于重建和回退，不维护长期多版本兼容层。支持范围变更和基线提升由 SIG 确认。

安装指南或发布说明应提供当前基线的验收与 SIG 决策记录入口；尚未完成首次验收时明确标注。安装版本不自动等同于已验收基线。基线记录包含以下信息：

| 内容 | 记录要求 |
|---|---|
| 代码与环境 | 本仓和 TorchTitan 完整 SHA、额外 diff；相关 Python、PyTorch、torch_npu、CANN、驱动/固件及算子依赖版本 |
| 安装与构建 | 子模块、补丁及顺序、关键构建选项、依赖解析结果；自建制品的来源、标识与校验值 |
| 验证范围 | 模型、配方、实际执行环境、精度、并行与配置；涉及设备时记录型号、数量与拓扑 |
| 证据与回退 | 复现入口、报告、评审结论、限制和上一可用基线；首次建立时注明无历史基线 |

采纳某项能力仅表示纳入工作范围。按具体组合记录支持状态，不能将组内一个用例的结果推广至整组：

- **未验证**：证据不足，不推断可用或不可用。
- **实验性**：开放试用，列明已验证部分与限制，未作正式支持承诺。
- **正式支持**：约定范围通过验收，维护责任与所需资源已落实。
- **不支持**：有明确限制并记录原因；撤销已有承诺需说明迁移或弃用安排。

用例结果、验收结论和支持承诺分别记录，前两者的状态见第 5 节。组件或功能的正式支持不等于模型训练收敛；长期收敛证据按声明范围要求。数值、功能、性能和长期训练分别给出证据。现有局部实验不会因列入文档而升级为正式支持。

## 3. 变更与评审

### 何时需要 RFC

架构或维护与支持策略变化、重大或不兼容的公共接口变化、引入或替换长期依赖，以及存在重要取舍的优化方案，应在社区创建标题以 `[RFC]` 开头的 issue。以 issue 编号标识提案，不另设仓库 RFC 文件编号；在 issue 中维护方案、讨论和决议，关联实现或文档 PR。通过评审的长期策略和技术设计分别更新本文及架构或组件文档，不要求将提案全文入仓。沿用既定策略的模型/特性适配、兼容接口扩展、常规依赖升级、局部修复和文档修改，可在 issue 或 PR 中说明方案；支持组合的新增或撤销仍需显式评审，但不一律要求另写 RFC。

RFC issue 正文记录提案状态为 `Draft`、`Accepted`、`Rejected`、`Deferred`、`Implemented`。接受方案表示同意实施方向；标记 `Implemented` 需关联实现和验收证据。方案讨论期间可验证假设，不能将实验结果代替采纳决定。

### 公开评审

本仓属于 [Ascend for PyTorch Distributed SIG](https://gitcode.com/Ascend/community/blob/master/AscendForPyTorch/sigs/distributed/README.md)。Maintainer、Committer 公开名单及联系入口以该页面为准；维护者在 PR 中协助确认适用的评审人和 SIG 决策安排。

任何贡献者都可以在 issue、PR 或 RFC 中提出方案、请求评审或协助验证。PR 可以在验证未完成时提交，需说明待完成项；以下合入条件在合入前满足。维护者协助确认实现归属、所需检查和相关评审，非作者评审者审查实现、结果和限制，具有相应权限的维护者确认结论并执行合入或发布。

方案、评审意见和决议保存在关联讨论中；其他渠道形成的结论需回写并说明理由。存在分歧时记录待解决问题，由具有相应决策职责的维护者或 SIG 明确接受、拒绝或暂缓；未回复不视为接受。必需验证缺失时保持待验收，不能以决议代替实测结果。

普通变更由维护者评审。每个 PR 至少取得一位 maintainer 的 approve 和两位 committer 的 lgtm，作者不能批准自己的变更。支持范围变更、基线提升、新增运行时补丁、基础依赖源码补丁例外，以及架构或维护策略变化须由 SIG 确认。SIG 负责人或授权代表在关联 RFC、issue 或 PR 中记录决策人、日期、范围和条件，不强制开会或全员投票。SIG 决策不替代 PR 评审门槛或必需验证。

### 合入条件

1. 说明问题、范围、实现归属和兼容影响，按需关联已有任务。按[设计原则](../ARCHITECTURE.md#设计原则)核对扩展接口及资源的创建、使用和释放责任；新增或扩大违反设计原则的实现不能按普通适配合入，已有偏离单独整改，不要求无关 PR 顺带迁移。
2. 按影响预先确定必需检查、比较对象及通过标准；复用已有检查，补充有实际价值的回归测试。
3. 必需检查通过，结果关联受测提交。影响 NPU 训练或算子执行时验证相关设备路径；配置检查只证明配置，文档修改只需相关文档检查。
4. 同步受影响的安装、模型、补丁和支持说明，检查同类调用与引用。
5. 取得上述 maintainer approve、committer lgtm 及适用的 SIG 决策，解决阻塞性意见，记录结论；未完成评审不能将验收结论记为通过。

局部修改可将检查结果直接写在 PR 中；新增能力声明、基线升级和发布按第 5 节记录适用的验证范围、受测组合、结果与评审结论；结果可记录在 issue、PR 正文或可追溯报告中，不强制提交到仓库。实现评审、验收和支持决策可在同一 PR 中分别记录，无需额外审批单。共享环境与配置引用一次，仅补充本次差异。

后续改动影响执行路径、依赖或配置时，重跑相关检查；沿用旧证据需说明适用依据。实验性能力也须满足本次合入的必需检查，不能用状态标签豁免验证。

## 4. 上游升级与补丁

### 候选与升级节奏

持续跟踪 TorchTitan main，以 PyTorch 正式版本及配套 Ascend 软件栈为主要升级节奏。上游切换 PyTorch 版本线前最后一个适用的 TorchTitan 提交作为候选起点，不强制选用；结合依赖变化、实际接口和回归情况核定 SHA，记录选择依据。必要修复可触发计划外更新，仍须完整完成该次声明范围内的必需验收。上游重要发布触发重评，不自动切换到 tag。

日常探测可使用明确的 nightly 构建；发布原则上使用目标 PyTorch 正式版本及配套制品、Ascend 软件栈。经 SIG 批准的基础能力阻塞源码补丁例外，按[补丁准入与退出](#补丁准入与退出)构建、追溯并验收实际交付组合，不能以 nightly 或未打补丁组合的结果代替。不承诺固定周期或与上游同日发布。

每次升级按以下流程执行，不要求将每个上游提交都变为本仓基线：

1. **选择候选**：记录旧/新 SHA，分类相关变化为直接复用、需要适配、依赖后端修复、暂缓或无关，并说明依据。
2. **确认环境和方案**：固定兼容的软件栈，核对接口、默认行为和补丁；新增核心能力先更新候选及采纳记录。
3. **验证**：选择受影响的既有承诺和新增场景，确定必需用例；完成适配与受控对照，记录无法保持一致的条件及失败归因。
4. **评审并提升基线**：必需项通过且 SIG 确认后，同步基线、安装说明、补丁清单和支持记录，保留上一可用组合。

候选失败时保留原基线并记录问题，不阻断与其无关的基线内开发。不得通过删除失败用例静默缩减支持范围。PR 回归、候选探测和发布检查均须留存证据，人工执行与 CI 使用相同的判定标准。

### 补丁准入与退出

配方配置、组件 override 和公开接口注册属于正常适配，不作为补丁管理。通用缺陷向所属上游贡献，优先使用已合入的明确提交或可追溯制品；不要求修复必须等待上游正式 release，但所选组合仍须验收。

**依赖源码补丁原则上不进入正常安装和发布。** 根目录 `fixes/` 用于保存 PyTorch、torch_npu、triton-ascend 等非 TorchTitan 仓库的源码补丁，供历史版本重建、开发验证，以及经 SIG 批准的基础能力阻塞例外使用。具体应用步骤只在对应版本安装文档中说明。TorchTitan 问题优先通过上游修复、正式扩展点或下述局部运行时补丁处理，不纳入该源码补丁目录。

基础依赖源码补丁进入发布须同时满足：

1. 有证据证明阻塞选定的最小训练流程或既有支持能力，不用于仅提升性能的优化；兼容版本、配置和正式扩展接口无法合理解决。
2. 向所属上游提交修复 PR，记录影响范围、上游状态、维护责任人和退出条件；补丁仅包含必要运行改动，不修改与修复无关的上游文案和注释；对应上游 PR 包含测试。
3. SIG 明确批准例外范围；固定依赖 SHA、补丁内容及顺序、构建方式、制品标识与校验值。不得通过私有 fork 或预打补丁的 wheel 隐藏未经批准的改动。
4. 实际交付的含补丁组合完成全部必需验收，安装文档公开说明例外，不能借用其他组合的结果。
5. 每次基线提升重新经 SIG 审查；修复进入所用依赖后移除补丁并回归。上游拒绝或长期未处理时重新评估，不自动成为永久分叉。

**局部运行时补丁**采用显式 monkey patch，只服务当前基线。新增 patch 必须经 SIG 评审。准入要求为：问题可复现，配置、本仓调用点、正式接口或兼容依赖无法合理解决；仅修正局部可选依赖加载、保持语义的参数转发或非计算性辅助问题，不改变计算、状态、调度、并行或精度语义，不承担多版本兼容。必须证明应用时机可控、重复调用幂等，记录上游 PR/问题、适用范围、维护人和退出条件。

运行时补丁验收覆盖原问题复现、修复后行为、范围外行为及真实错误仍暴露、独立进程启动与重复初始化，以及受影响路径的集成回归。接口转发通往计算路径时验证相关数值和梯度。每次升级重新审查必要性；修复进入依赖后移除并回归。

无可用替代且不满足例外条件时，新能力不进入发布；已有基线可用则保留并跟进，已有支持受影响时公开记录并修复或回退。不得把底层源码问题强行改为 monkey patch 绕过准入。

源码补丁记录见 [fixes/README.md](../fixes/README.md)，运行时实现见[补丁说明](../torchtitan_ascend/patches/README.md)。现有补丁须按本文准入边界逐项评审，不自动获准进入新发布；历史组合保留重建信息。

## 5. 验收规则

### 按影响选择检查

专项验收方案仅约束对应任务，不作为全仓通用门槛。基线升级的完整验收指完成该次声明范围内全部必需项，不等于执行所有候选能力。无需为每次变更执行全矩阵或重复填写所有类别；在计划中解释被排除的相关场景即可。

数值与性能的具体执行要求分别见 AGENTS 中的[数值与训练质量](../AGENTS.md#数值与训练质量)和[性能测试](../AGENTS.md#性能测试)，按本节确定的适用范围执行。

| 类别 | 适用场景与所需证据 |
|---|---|
| 基础检查 | 相关静态、配置/导入、安装与文档检查；按变更类型选择 |
| 短程运行 | 训练路径变化或新配方：预定步数、有限 loss/梯度、目标参数更新 |
| 数值正确性 | 计算路径变化：适用的输出与梯度对照、代表性形状及相关整网指标 |
| 功能 | 状态或行为变化：声明功能的实际用例；恢复训练检查模型、优化器、调度器、随机状态与数据进度，分布式使用真实进程组 |
| 性能 | 收益声明：可比较的基准、原始测量、重复统计及正确性回归 |
| 长期训练 | 收敛或持续稳定性声明、可能影响训练质量的变化：与拟声明范围相称的数据、训练规模、质量指标与曲线 |

### 对照与结论

- 记录实际配置、数据及顺序、tokenizer、初始权重、种子、精度、优化器、训练规模与启用特性。相同种子不保证输入和初态相同；可引用配置与附件而不逐处复制。
- 预期计算不变且条件支持确定性时验证一致性。跨硬件、低精度或非确定性差异需预先约定误差指标与容差依据；标准确需调整时保留理由、评审与重新验证记录，不能为了让当前失败通过而回填标准。
- 性能测量说明控制变量、预热、编译和数据准备是否计时、测量区间、设备同步或事件计时、重复次数与统计方式，以及吞吐和峰值显存口径。披露波动和取舍；没有可执行比较对象时只报绝对指标，不宣称相对加速。
- 结论限定实际模型、数据、硬件、精度、配置与步数/tokens。短程 loss 下降不证明长期收敛，单算子或单卡通过不证明整网或多卡通过。

### 结果与评审

用例状态只使用“通过”“失败”“未执行”“不适用”。skip 计为未执行；不适用需说明范围依据并在评审中确认。缺少资源不是不适用，退出码为零不能替代必需用例实际通过。

报告状态统一为：必需项存在失败时为**未通过**；无失败但缺少必需结果时为**待验收**；必需项通过但尚未评审时为**待评审**；结果和限制获评审同意后为**通过**，评审否决则为**未通过**。可选项的失败或缺口也需披露并说明是否影响结论。

保留失败与重跑的对应记录，区分环境故障和产品缺陷；间歇性失败需解释和后续处置，不能只展示成功的一次。证据应可定位、可复现，记录受测提交和稳定的访问入口；大型日志可放在 issue 附件或制品存储，报告只保留摘要及链接。完成报告须记录真实执行者、评审者和实际执行环境；纯 CPU 或文档检查不要求 NPU 资源。

## 6. 发布与回退

按基线就绪情况发布，采用本仓独立版本号，发布记录明确 TorchTitan SHA 与 PyTorch/Ascend 软件栈映射，不强行与依赖版本号一致。基线与支持范围已经 SIG 确认且发布候选无实质变化时，由维护者完成发布检查和操作，无需重复决策。

按本次声明范围验收和发布。发布前确认：

- 候选对应明确提交与依赖基线；干净环境的安装和最小运行通过，发布制品时验证实际候选制品。
- 声明范围的必需检查通过并完成评审；正式支持已落实维护责任和资源，实验性范围明确限制。
- 发布说明包含能力与行为变化、依赖和补丁、已知限制、迁移方法及上一可用基线；首次发布注明无历史发布版本，已有基线回退选项照实记录。

回退需重建对应代码、依赖与补丁组合。检查点及导出产物兼容性另行说明，回退代码不代表可无损续训。发现发布回归时记录受影响版本与场景，更新限制并验证修复或回退路径。

## 7. 文档职责
